## Block / dodge mutual exclusion (v8) — user-requested rule change

**User's rule:** *"you cannot dodge or block at the same time. When blocking, dodging is off limit, and vice versa."*

**The gap this closed:** the v7 code only enforced one direction. `IsBlocking = blockHeld && !IsDodging` meant a dodge suppressed blocking, but **you could still start a dodge while holding block** — `StartDodge()` was gated only on `!IsDodging` and the cooldown. So the two could overlap on the dodge's first frame.

**The fix, in `PlayerCombat.Update`:** compute the block intent *first*, then gate the dodge on it.

```csharp
bool wantsToBlock = blockHeld && !IsDodging;

if (dodgePressed && !IsDodging && _dodgeCooldownTimer <= 0f)
{
    if (wantsToBlock) { /* refused - must release block first */ }
    else { StartDodge(); wantsToBlock = false; }   // dodge owns the frame
}

IsBlocking = wantsToBlock;
```

**Why this is airtight:** `IsBlocking` is now only ever assigned `blockHeld && !IsDodging`, and `StartDodge()` is unreachable while `wantsToBlock` is true. So `IsBlocking && IsDodging` is structurally impossible — there is no frame on which both can be true. Verified by hand across all four cases (dodging / blocking / neutral / stunned).

**Deliberate consequence:** releasing block and pressing E on the *same* frame **is** allowed, because `blockHeld` is read fresh each frame. Only a *held* block refuses the dodge. This is the forgiving reading and matches "release block, then dodge".

**Discoverability:** refusing the dodge silently would feel like a broken input, so `PlayerCombat` gained `DodgeRefusedRecently` (a short `dodgeRefusedFeedbackDuration = 0.9s` window) plus an `OnDodgeBlockedByBlock` event. `StaminaBarUI` polls the property and shows *"Release Q to dodge — you cannot block and dodge at once"*. The BLOCKING status line now also reads "dodge locked out". Polling was chosen over subscribing so `StaminaBarUI` needed no new event wiring.

## Manager architecture — foundation + match spine built

User skipped the scoping questions, so I used judgement and built the foundation plus the match spine. All in **`Assets/Scripts/Manuel/Managers/`**, namespace `ProjectLEA.Manuel.Managers`.

| File | Owns |
|---|---|
| `ManagerBase.cs` | CRTP singleton: `ManagerBase<T> where T : ManagerBase<T>`, `Instance` / `Exists`, virtual `OnManagerAwake()` to override instead of `Awake` |
| `ScoreManager.cs` | Points, `PlayerSlot` enum, `OnPointScored` / `OnMatchWon` |
| `SpawnManager.cs` | Spawn points by name prefix, two generated fallbacks either side of origin |
| `RoundManager.cs` | Round number, start/end, respawn both slots |
| `GameManager.cs` | `MatchState` machine: Idle → Warmup → RoundActive → RoundOver → MatchOver |
| `ManagersBootstrap.cs` | Creates `[Managers]` at runtime via `RuntimeInitializeOnLoadMethod(AfterSceneLoad)` |

**Key decision — managers are created at RUNTIME, not authored into the scene.** Editing the scene from outside the Editor has been the single most fragile part of this project (marker/reload ordering, compile errors blocking the build, the body-placeholder wipe). Runtime creation removes that entire class of problem: the bootstrap adds the components if they are not already present, so a hand-placed `[Managers]` object also works.

**Two bugs caught before handoff, both classic Unity/C# traps:**
1. **`private void OnDestroy()` hides `ManagerBase.OnDestroy()`.** Unity dispatches the message to the most-derived method, so the base would never run and `Instance` would never be cleared. Fixed to `protected override void OnDestroy() { ...; base.OnDestroy(); }`. **Any future manager that needs a Unity message the base also defines must use `override`, not a new method.**
2. `Object` is ambiguous between `System.Object` and `UnityEngine.Object` (**CS0104**) whenever a file has both `using System;` and `using UnityEngine;`. The manager files avoid bare `Object` entirely; `CleanSlateSetup.cs`/`RestorePlayerBody.cs` qualify it as `UnityEngine.Object`.

**Not yet built:** `UIManager`, `AudioManager`. Also still open: the network-authority decision (Score/Round/Economy must be server-authoritative in a real PvP build — the current design already has "one authority writes, everyone else reacts via events", which is the shape that survives it).

## Class + weapon system (v11) — built

**User correction worth remembering:** magic, shields, traps and turrets are **class abilities, NOT weapon categories.** The first draft of `WeaponCategory` had `Shield`/`Deployable`/`Ability` in it and that was wrong. Final set is purely about how a weapon is *delivered*: **Melee, Gun, Bow, Thrown, Launcher**. Abilities live separately in `AbilityDefinition` + the class's `abilityPrefab`.

**The "add a class, then attach a script for its abilities" mechanism:** `ClassDefinition.abilityPrefab` points at a prefab whose components implement `IClassAbility` (`OnEquipped` / `OnUnequipped` / `OnActivated`). `ClassAbilityHost` (on the Player) instantiates it on class pick and drives the cooldowns from `AbilityDefinition`. ## Blurry UI text — root cause and fix

**User report:** the loadout screen text was very blurry. Asked for it to work at **1920 × 1200** and "theoretically on every device".

**Root cause:** legacy `UnityEngine.UI.Text` rasterises glyphs into a font atlas at `fontSize`, then the canvas `scaleFactor` scales the resulting mesh. So whenever the canvas scales — which is exactly what `CanvasScaler.ScaleWithScreenSize` does — the text is resampled and goes soft. It is worst when upscaling, but downscaling a rasterised glyph also softens it. **There is no way to make legacy Text crisp under canvas scaling**; it is the specific problem TMP exists to solve.

**Fix: TextMeshPro, with the font built at runtime.** TMP draws from a signed-distance-field atlas so it stays sharp at any scale. Two things had to be checked first:

1. **TMP ships inside `com.unity.ugui` 2.0.0 in Unity 6** — there is no separate `com.unity.textmeshpro` package, and the runtime assembly `Runtime/TMP/Unity.TextMeshPro.asmdef` is present, so `using TMPro;` compiles.
2. **TMP Essential Resources are NOT imported** in this project (no `Assets/TextMesh Pro/Resources/TMP Settings.asset`), which would normally mean no default font asset and therefore no visible text.

**The workaround that avoids needing Essentials:** `TMP_FontAsset.CreateFontAsset(Font)` builds a usable TMP font asset at runtime from Unity's built-in font. Confirmed present in the package source (`TMP_FontAsset.cs:538`). So `LoadoutUI` builds its own TMP font on first use.

**Fallback chain (important — this cannot be allowed to show nothing):** try the runtime TMP font → if it throws or returns null, use legacy `Text` and log a one-line hint telling the user to import TMP Essentials. A private `Label` wrapper holds whichever component was created, so nothing else in the file knows or cares which it got.

**Also:** `referenceResolution` is now **1920 × 1200** (was 1920 × 1080), `matchWidthOrHeight = 0.5` so it adapts to other aspect ratios.

**Note on the screenshot:** it was downscaled from 1920 to ~1082 px, so *everything* in it looked soft, including the Unity menu bar. Some of the perceived blur was a capture artefact — but the underlying legacy-Text scaling problem was real and is now fixed.

```
TMPro.TMP_FontAsset:CreateFontAsset ... (TMP_FontAsset.cs:565)
```

**`TMP_FontAsset.CreateFontAsset(Font)` cannot work with `LegacyRuntime.ttf`/`Arial.ttf`** — Unity's built-in fonts ship without readable font data, so `FontEngine.LoadFontFace` fails and TMP returns null. There is no way to fix that from code. TMP only works here once **TMP Essential Resources** are imported (`Window > TextMeshPro > Import TMP Essential Resources`), which provides `TMP_Settings.defaultFontAsset`. `GetTmpFont()` now only consults that setting and no longer attempts `CreateFontAsset`.

**Also note:** the failure was silent from my side — `CreateFontAsset` returned null *without throwing*, so my try/catch never fired and no warning was logged. Only TMP's own internal log line revealed it. **When a "graceful fallback" path exists, check the log for what the fallback actually did** — the code looked like it was working.

## The real fix for blurry text: scale factor 1

Since TMP was unavailable, the blur had to be fixed at the source. **Legacy `Text` rasterises glyphs at `fontSize`, then the canvas `scaleFactor` scales the mesh — so any scale ≠ 1 resamples the text.** No amount of fiddling with `CanvasScaler.ScaleWithScreenSize` avoids that.

So `LoadoutUI` now does the opposite:
- `CanvasScaler.uiScaleMode = ConstantPixelSize`, `scaleFactor = 1` — a true 1:1 pixel mapping
- The class scales everything itself: `S(value)` for sizes, `F(fontSize)` for font sizes, both multiplied by `_uiScale`
- `_uiScale = min(Screen.width / 1920, Screen.height / 1200)`, clamped to ≥ 0.2 — matches the **smaller** axis so the layout always fits
- **Rebuilds the canvas when `Screen.width/height` change**, because font sizes are baked in at build time

Result: text is rasterised at exactly the pixel size it is drawn at, at any resolution or window size.

**Bug caught before handoff:** `Rebuild()` originally called `SetOpen(_isOpen, instant: true)`. While the panel is open the cursor and `Time.timeScale` are already overridden, so `SetOpen` would re-capture *those* values as the "previous" state — and closing the panel would then restore `timeScale = 0`, freezing the game permanently. `Rebuild` now restores panel visibility directly instead.

**Confirmed working from the log before this change:** `ManagersSetup` ran at 13:11:27Z and created `[Managers]` (all 8 components) + added `ClassAbilityHost`, `WeaponUser`, `Health` to the Player + `TrainingTarget` at `(0,1,6)`. The scene contains `Player`, `FirstPerson Camera`, `Directional Light`, `Global Volume`, `TrainingTarget`, `BodyPlaceholder`, `[Managers]`. Test seeding also fired correctly. So the only thing actually broken was the text rendering.

**Confirmed fixed:** the user's next screenshot showed crisp text at 1080p. The scale-factor-1 approach works.

## Shop: overlapping text, confirm button, buy/sell (v14)

**Overlap cause:** in `CreateRow`, the title and detail each took *half* the row — title `anchorMin (0, 0.5)` / `anchorMax (1, 1)`, detail `(0,0)` / `(1,0.5)`. Their text therefore met exactly at the midline and read as overlapping. **Fix:** give each line its own fixed-height box anchored to the top of the card — title 32 tall at 6 from the top, detail 22 tall at 42 from the top, row height 80. There is now a guaranteed gap. *Sharing a container by halves never leaves a gap; use explicit offsets when two lines must not touch.*

**Buy/sell model — one carried weapon at a time.** `WeaponManager.Purchase` sells the equipped weapon first (via the private `Sell(index, quiet: true)`), counts the refund toward the purchase, and if `money + refund < cost` it **puts the weapon back** (`RestoreOwnership`) so a failed purchase changes nothing. This matches the user's Valorant example exactly: 800 → buy an 800 weapon → 0 → still able to buy a 500 one, because selling the first returns the 800. `sellRefundRatio` (default 1.0 = full refund) is exposed so swapping can be made to cost something later. New API: `TrySell`, `GetSellValue`, `IsEquipped`, `ProjectedBalanceAfterBuying`, `CanBuy`.

**UI:** left-click buys+equips (auto-selling the previous), **right-click sells**, and a **CONFIRM button** bottom-right which is disabled and reads "PICK A CLASS" until a class is chosen. Cards now show the price right-aligned — `EQUIPPED` / `SELL n` / cost.

**CRITICAL — mouse look must be disabled while a menu is open.** `Time.timeScale = 0` stops movement but **mouse delta is NOT scaled by timeScale**, so the view kept swinging around behind the shop. Fixed by adding `PlayerController.InputEnabled` (default true); `ReadInput` returns early and the jump check is guarded when false. `LoadoutUI` sets it false on open and true on close. **Any future full-screen menu must do the same** — timeScale alone is not enough.

## Class abilities: interface fixed + a worked example (v15)

**`IClassAbility` was under-specified and the host was wrong.** The old host looped over every ability and called `OnActivated` on **all** of them when any key was pressed — so with two abilities, pressing one key fired both. It also gave the script no access to its own tuning data.

**Fixed interface:**
```csharp
string AbilityName { get; }                                  // matched against AbilityDefinition.displayName
void OnEquipped(GameObject player);
void OnUnequipped(GameObject player);
void OnActivated(GameObject player, AbilityDefinition ability);   // tuning data handed in
```

`ClassAbilityHost` now builds a `definition -> matching components` map (`_bindings`) and fires **only** the scripts that claim the ability. A component whose `AbilityName` matches nothing is still equipped but never fired — **that is how a passive is written**. It also logs a warning when a script names an ability the class does not have, because the alternative symptom is simply "the key does nothing", which is undiagnosable.

**`Assets/Scripts/Manuel/Abilities/SampleDashAbility.cs`** — a working example and the template to copy. Drives the dash through `PlayerController.ExternalMotionLock` / `ExternalVelocity` (the same channel the old dodge used), and scales its distance by `ability.power / referencePower` so tuning stays in the class data. `Stop()` always returns the controller, and it is called from `OnUnequipped`, `OnDisable` and when the dash ends — **never leave `ExternalMotionLock` true or the player is permanently immobile.**

## Drag-and-drop loadout: weapons and classes are now ScriptableObjects (v16)

**User ask:** *"our manager should change since i want a more drag and drop for weapons in the inspector... imagine u building the thing all i have to do is drag and drop."*

**The change:** `WeaponDefinition` and `ClassDefinition` went from `[Serializable]` classes embedded in the manager to **`ScriptableObject` assets** with `[CreateAssetMenu]`. One asset per weapon/class, edited in its own Inspector, dragged into the manager's list. This is the standard Unity content workflow and it is what "drag and drop" actually means.

- `WeaponManager.catalog` → `List<WeaponDefinition>` — now **asset references**, so drag-and-drop works in the Inspector
- `ClassManager.classes` → `List<ClassDefinition>` — same
- **`ClassDefinition.allowedWeapons` changed from `List<string>` (weapon display names) to `List<WeaponDefinition>` (asset references).** Names were fragile — renaming a weapon silently broke every class's allow-list. References cannot drift, and they are drag-and-drop too.
- `ClassDefinition.AllowsWeapon(WeaponDefinition)` now uses `List.Contains` instead of case-insensitive string matching.

**Consequences worth remembering:**
1. **`new WeaponDefinition()` no longer compiles** — ScriptableObjects must be made with `ScriptableObject.CreateInstance<T>()`. The runtime seeding was rewritten to use a `TestWeapon(Action<WeaponDefinition>)` / `TestClass(Action<ClassDefinition>)` helper, which keeps the configure-in-place style without object initialisers.
2. **The `PropertyDrawer` had to be deleted.** A `[CustomPropertyDrawer]` only applies to a field drawn inline; a ScriptableObject gets its own Inspector, so `WeaponDefinitionDrawer.cs` was replaced by **`WeaponDefinitionEditor : Editor`** (`[CustomEditor(typeof(WeaponDefinition))]`), which draws the same category-conditional fields and adds a read-only summary box showing the derived flags.

**`Assets/Scripts/Manuel/Editor/LoadoutAssetTools.cs`** — the drag-and-drop helpers:
- `Tools > Manuel > Loadout > Create Test Weapons (5 assets)` / `Create Test Classes (2 assets)` — writes real assets to `Assets/Data/Manuel/Weapons|Classes/` **and** appends them to the manager's list via `SerializedObject` (`FindProperty("catalog")` / `("classes")` + `arraySize++`).
- `[CustomEditor(typeof(WeaponManager))]` and `[CustomEditor(typeof(ClassManager))]` — each adds a **"Add every weapon/class asset found in the project"** button (`AssetDatabase.FindAssets("t:WeaponDefinition")`) plus a button to create the test batch. This is the "you build it, I just click" convenience the user asked for.

**Note:** `WeaponDefinition` is still referenced by value in `DamageInfo.weapon`, `WeaponUser`, and the `WeaponManager` events — all unchanged, since an asset reference is just a reference.

## Round and point system (v17)

**The spec, confirmed with the user after asking** — the original message was self-contradictory ("5 kills = 1 point" vs "first to 10 points wins"), so I asked rather than guessed:

| Rule | Value |
|---|---|
| Start the match | **P** |
| First buy phase | **30s**, ends on timer or both players confirming |
| Round | **1:40** (100s) |
| Round timer expires | **45s overtime**, then whoever has more HP takes it |
| Kills per point | **5** |
| Points to win | **10** |
| After a **kill** | 15s buy, weapons only, **class locked** |
| After a **point** | 30s prep, **class can be re-picked** |
| Debug keys | **N**/**M** = player 1/2 dies, **J**/**K** = award a point directly |

**The two-level structure is the key insight:** a kill and a point are different events with different consequences. A kill only reopens the weapon shop; a point also unlocks the class. `GameManager.RegisterDeath` branches on `ScoreManager.RegisterKill`'s return value, which is true exactly when that kill converted into a point.

**Files:**
- `ScoreManager` — kills, points, and **loss streaks**. `RegisterKill` returns true when the kill converted to a point. `RecordRoundResult` grows/clears streaks.
- `EconomyManager` — now **per-slot balances** (`int[2]`) because it is a 1v1: win reward, smaller loss reward, plus a capped per-loss bonus. `Money` stays as shorthand for slot One, which is what the shop spends.
- `GameManager` — the phase machine: `Idle / Buying / RoundActive / Overtime / KillBuy / Prep / MatchOver`. Owns the timers, the debug keys and `ConfirmReady`.
- `PlayerTwoDummy` — a damageable body registered as `PlayerSlot.Two`, so the round loop has an opponent.
- `MatchHud` — phase, countdown, per-player kills/points/money/streak, and the winner banner.
- `SettingsMenu` — ESC panel.

**CRITICAL — all phase timers use `Time.unscaledTime`, not `Time.time`.** The shop sets `Time.timeScale = 0` while open, which would freeze a `Time.time`-based buy countdown so it never expired. Unscaled time keeps the countdown running while the shop is open, which is exactly what a buy phase needs.

**Death flows through exactly ONE path.** `Health.Die()` used to award a point itself *and* `GameManager.RegisterDeath` awarded another, so a real death scored twice. `Health` now only raises `OnDied`; `GameManager` subscribes to both players' `Health` and runs everything through `RegisterDeath`. The subscription is **retried every frame** (guarded by a per-slot bool) because the second player may register after `Start` — Awake order between scene objects is undefined.

**The shop is now phase-gated.** `LoadoutUI` opens on entering a buy phase and closes when the round starts, via a `_lastPhase` comparison. **B does nothing mid-round** — no shopping during a live round. CONFIRM now calls `GameManager.ConfirmReady(PlayerSlot.One)` rather than just closing.

## Settings menu rebuilt — centred, sliders, display and graphics options (v18)

**User feedback from a screenshot:** the panel was **left-aligned rather than centred**, and the click-to-adjust rows should be **sliders**. Plus: fullscreen/borderless, aspect ratios, and proper graphics options (AA, v-sync, volume).

**Rewritten `SettingsMenu`:**

- **Centred card over a full-screen dimmer.** The old version anchored everything to the top-left. Now there is a `Backdrop` stretched to the screen plus a `Panel` at `anchorMin/Max (0.5, 0.5)`, `pivot (0.5, 0.5)`, `anchoredPosition zero`, fixed size. **Centring a panel is `anchorMin == anchorMax == (0.5,0.5)` with pivot (0.5,0.5) and a zero position** — anchoring to a corner is what made it hug the edge.
- **Three sliders:** mouse sensitivity, field of view, master volume.
- **Six cycle rows:** display mode, resolution, V-Sync, anti-aliasing, FPS cap, quality level.

**Sliders are hand-rolled, and that is deliberate.** uGUI's `Slider` needs an `EventSystem` plus an `InputSystemUIInputModule` created at runtime with valid default actions — the same two things the shop already avoids. The manual version: on mouse-down anywhere on the row start a drag, convert the pointer to local space with `RectTransformUtility.ScreenPointToLocalPointInRectangle`, map `local.x` from `[-w/2, +w/2]` to `[0,1]`, and drive the fill's `anchorMax.x`. Works with no EventSystem at all.

**Display:** `FullScreenMode.ExclusiveFullScreen` (Fullscreen) / `FullScreenMode.FullScreenWindow` (Borderless) / `Windowed`, applied through `Screen.SetResolution`.

**Resolutions are a curated list, not `Screen.resolutions`** — that returns dozens of near-duplicates. The list covers 16:9, 16:10, 4:3 and 21:9 so every aspect ratio the game might run at is reachable, and `Describe()` labels each with its ratio.

**Anti-aliasing reads and writes `UniversalRenderPipelineAsset.msaaSampleCount`**, falling back to `QualitySettings.antiAliasing` when there is no URP asset. `QualitySettings.antiAliasing` is kept in step too. Confirmed `Unity.RenderPipelines.Universal.Runtime` is referenced by `Assembly-CSharp.csproj`, so the URP types compile.

**Caveat worth remembering:** `msaaSampleCount` lives on the **pipeline asset**, so changing it at runtime dirties the asset and the change persists in the Editor. That is fine for tuning but would not survive into a build — a real game would write it to a saved settings file and reapply on load.

## Settings polish + main menu (v19)

**Clipped labels — root cause was an arithmetic slip.** The row is `panelWidth - 80 = 920` wide, but the slider value label sat at local x=820 with width 140 (→ 960) and the cycle value label at 380 with width 580 (→ **960**). Both ran past the row's 920 and up to the panel edge, so the text looked cut off. **Lesson: when laying out inside a fixed-width row, add the offset and the width and check it against the row width — do not eyeball it.**

Fixed layout, all inside 920 with margin:
- label `20..320`, track `340..720`, value `730..900`
- cycle value `400..900`

**Sliders now read as sliders:** track height 16 → 24, plus a **knob** (22×36) anchored to the value position, so it is visibly draggable rather than looking like a progress bar. The whole row is still the grab area, which is more forgiving than a thin track.

**TAA needed a second, separate setting.** URP has **two independent anti-aliasing systems** and they are not the same control:
1. **MSAA** — `UniversalRenderPipelineAsset.msaaSampleCount` (Off/2x/4x/8x)
2. **Camera post-process AA** — `UniversalAdditionalCameraData.antialiasing` = `AntialiasingMode.None / FastApproximateAntialiasing (FXAA) / SubpixelMorphologicalAntiAliasing (SMAA) / TemporalAntiAliasing (TAA)`

**TAA lives only in the second one.** Both rows are now exposed. **SMAA and TAA are applied by the post-process pass, so `renderPostProcessing` must be true or they silently do nothing** — the step method turns it on when either is selected. Reached via `camera.GetUniversalAdditionalCameraData()`.

**Main menu added:**
- `Assets/Scripts/Manuel/Managers/MainMenuUI.cs` — PLAY / SETTINGS / QUIT, built entirely at runtime so the scene needs a single GameObject. It creates a Camera if the scene has none, and **reuses the same `SettingsMenu` component** rather than duplicating the panel. PLAY checks `Application.CanStreamedLevelBeLoaded` before loading and says so if the scene is not registered.
- `Assets/Scripts/Manuel/Editor/MainMenuSetup.cs` — `Tools > Manuel > Create Main Menu` creates `Assets/Scenes/MainMenu.unity`, and `RegisterScenes` puts **MainMenu first, then Manuel** in Build Settings while preserving any scenes already registered.

**Two fixes along the way:** `SettingsMenu.SetOpen` had to become public (I first tried a `SendMessage("SetOpen", true)` to reach a private method — fragile and it would not have matched the optional parameter). And `ReadSensitivity`/`WriteSensitivity` needed a `_fallbackSensitivity`, because with no `PlayerController` — which is the case in the main menu — the write went nowhere and the slider snapped back on every drag.

**Still open:** settings are **not persisted** between sessions (no PlayerPrefs), and MSAA/AA changes dirty the pipeline asset rather than being stored anywhere.

**Honest note on `MatchHud.SetIfChanged`:** I added it believing per-frame `Text.text` assignment forced a mesh rebuild every frame and might explain the lag. That was **wrong** — Unity's `Text.text` setter already compares `m_Text != value` before calling `SetVerticesDirty`, and `Graphic.color` likewise guards equality. The change is harmless and reads more explicitly, but **it is not a performance fix** and the lag has some other cause. Worth remembering: check the actual setter before assuming an assignment is expensive.

**`SettingsMenu` deliberately does NOT pause** — no `timeScale` change, so the round timer keeps running and you are a sitting duck while it is open. It only unlocks the cursor and switches `PlayerController.InputEnabled` off so the rows can be clicked. Rows are adjusted by left-click (raise) / right-click (lower), which works with the hand-rolled hit-testing and needs no EventSystem. It exposed a need for `PlayerController.MouseSensitivity` as a settable property.
