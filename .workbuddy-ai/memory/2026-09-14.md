### Hand-authoring Unity scene YAML — pitfalls hit (IMPORTANT)

Writing `.unity` YAML by hand works, but **never invent GUIDs** — resolve each one from the real source first:
- `PlayerInput` script guid is `62899f850307741f2a39c98a8b639597` (get it from `Library/PackageCache/com.unity.inputsystem@*/InputSystem/Plugins/PlayerInput/PlayerInput.cs.meta`). Inventing one silently gives "Missing (Mono Script)".
- **Symptom of wrong GUID**: component shows `Missing (Mono Script)`, or the serialized field block below `m_Script` is ignored/cleared.
- Duplicate the **real serialized field set** for built-in components — read the class source. For `PlayerInput` the fields are `m_Actions`, `m_NotificationBehavior`, `m_UIInputModule`, `m_DeviceLostEvent`, `m_DeviceRegainedEvent`, `m_ControlsChangedEvent`, `m_ActionEvents`, `m_NeverAutoSwitchControlSchemes`, `m_DefaultControlScheme`, `m_DefaultActionMap`, `m_SplitScreenIndex`, `m_Camera` (NOT `m_ActionsAsset`/`m_MoveAction`/etc.).
- Global Volume profile guid must point at a profile that actually exists: `Assets/Settings/DefaultVolumeProfile.asset` = `ab09877e2e707104187f6f83e2f62510`. (The `10fc4df2…` guid in `SampleScene.unity` belongs to a package sample that is NOT in this project — do not copy it.)
- `Assets/InputSystem_Actions.inputactions` = `052faaac586de48259a63d0c4782560b`; contains a `Player` action map with `Move`/`Look`/`Jump`.

**Validation recipe (no Editor GUI needed):** the `Library/PackageCache` `*.cs.meta` files are the ground truth for package script GUIDs (`find Library/PackageCache -name "X.cs.meta"`).

### Movement feel fix (v5) — bob inversion + crouch speed + invisible player

**BUG 1 — bob was STRONGER when crouching than walking (user-reported, verified by simulation).**
Cause: `Mathf.Lerp(a, b, k * Time.deltaTime)` is **frame-rate dependent** and, at walking speed, the bob target oscillates faster than the lerp can chase it, so the sway got *averaged out and shrank* (1.87 cm walking vs 3.16 cm crouching — backwards).
Fix: replaced with frame-rate-independent exponential smoothing `t = 1 - Mathf.Exp(-swayDamping * Time.deltaTime)`, raised `swayDamping` 7 → 14, added explicit `crouchBobSuppression` (0.35) so crouch bob is deliberately reduced.
Verified by simulation across 30/60/144 fps: **walk 2.86 cm / crouch 0.69 cm**, near-identical across frame rates.
Amplitudes raised: `bobAmplitude` 0.045 → 0.05, `swayAmplitude` 0.035 → 0.04, `bobFrequency` 1.9 → 2.1, `strafeTilt` 1.1 → 1.2.

> **Rule: NEVER use raw `Mathf.Lerp(a, b, k * Time.deltaTime)` for smoothing.** Use `1 - Mathf.Exp(-k * Time.deltaTime)` instead, or the behaviour changes with frame rate.

**BUG 2 — crouch still too fast.** `crouchSpeed` 1.9 → **1.15** (77% slower than the 5 m/s walk, 4.35x).

**BUG 3 — player was invisible** (Player GameObject had no mesh at all). Added a **BodyPlaceholder** child object: Capsule mesh (`10208`), positioned at local y=0 so it spans local −1…+1 — exactly matching the CharacterController (height 2, center y=0). Uses `M_Platform` material.
Script field `bodyRenderer` added; in `Awake` it sets `shadowCastingMode = ShadowsOnly` so the placeholder **casts a shadow without blocking the first-person view** (and would be visible to remote players in the PvP build). Null-safe.

Serialized fields now **30**, all verified matching the scene block **in declaration order** with `diff`.

**Simulation-first practice that paid off:** writing a small Python re-implementation of the bob loop exposed the inversion immediately. Worth repeating for any tuned/accumulating motion code.

### Slide direction fix (v6)

**BUG — slide only ever went forward regardless of input.** `slideDir` was hardcoded to `transform.forward`.
Fix: slide now launches along the **input direction** `(transform.right * _moveInput.x + transform.forward * _moveInput.y)`, falling back to `transform.forward` when no movement key is held. Verified all 6 cases: W=forward, S=backward, A=left, D=right, W+A=forward-left diagonal, none=forward.

Two supporting fixes were required, or sideways/slow slides would have been impossible:
- **Entry gate** was `_horizontalVelocity.magnitude > moveSpeed * 0.5f` (2.5 m/s). Crouch-walking is only 1.15 m/s and strafing sideways is slower still, so slides from those states were blocked. Lowered to a flat `> 0.5f`.
- **End condition** was `< moveSpeed * 0.6f` (3.0 m/s), which would kill a slow-entry slide almost instantly. Changed to `< slideSpeed * 0.3f` (2.4 m/s) — relative to the slide's own launch speed.

Added `_slideDirection` (initialised to `Vector3.forward`) so **steering nudges the path instead of reversing it**: the steer vector has its component along the slide heading removed via `steer -= _slideDirection * Vector3.Dot(steer, _slideDirection)`. Verified: sliding right while pressing left yields a zero projection, so a slide can never be reversed mid-motion — it stays committed, which is what a PvP dodge needs.

**Note:** these were *private* fields only, so `Assets/Scenes/Manuel.unity` needed no change (still 30 serialized fields, verified matching).

**Unity batch-mode gotcha:** `-batchmode` fails with exit code 1 when `UnityPackageManager.exe` cannot start ("Could not connect to IPC stream", e.g. another Hub/Editor instance is holding things). Add `-noUpm` to skip the package manager and get past it. Note `Unity.exe ... | tail` in bash reports the *pipe's* exit code, so always read the real `-logFile` output rather than trusting `$?`.

### Unity cannot be launched from the agent shell at all (final diagnosis)

**Do not retry batch mode.** Established by elimination, with evidence:

- Stalls at `Application.AssetDatabase Initial Refresh Start` with **~1% CPU and zero `AssetImportWorker` processes** — hung, not slow. Reproduced with `-batchmode`, with `-noUpm`, with `-nographics`, outside the sandbox, and in **normal GUI mode** (`-projectPath` only). It is not batch-specific.
- **Not caused by our FBX.** Moved both FBX files out of `Assets` (verified empty) and Unity still stalled identically.
- **Not caused by sandbox env vars.** Tried `env -i` with a pristine Windows env (`SystemRoot`, `windir`, `TEMP`, `TMP`, `USERPROFILE`, `LOCALAPPDATA`, `APPDATA`, `comspec`, `PROGRAMDATA`, `HOME`) — same stall.
- **Not caused by stale locks.** Cleared `Temp/*`, `Library/*-lock`, `ArtifactDB-lock`, `SourceAssetDB-lock` — same stall.

**The sandbox virtualizes filesystem writes.** A `shutil.move` of the FBX *reported success* and `os.listdir` showed the files gone, but the real filesystem was unchanged (the move was discarded when the sandboxed process exited). This silently invalidated a whole isolation experiment. **Any real file move/delete must use `dangerouslyDisableSandbox: true`** — otherwise you will debug a filesystem that does not exist.

**UPM's `path undefined` bug has two faces.** With `Library/PackageManager` cache intact it *restores* resolved packages and works (`Registered 62 packages`). Once that cache is gone it must *re-resolve*, and then it fails again with `Failed to resolve packages: The "path" argument must be of type string. Received undefined. No packages loaded.` — a different code path from the `getLocalConfigFolder` startup crash. Unresolved; needs a complete user environment.

**Library caches were cleared this session** (`Artifacts`, `ArtifactDB`, `SourceAssetDB`, `Bee`, `ScriptAssemblies`, `ShaderCache`, `Search`, `PlayerDataCache`, `ImportLogs`, plus stale locks). All are regenerable; `PackageCache` and `PackageManager` were deliberately kept so packages resolve offline. **Consequence: the next Unity open does a full reimport** — expect a few minutes. This also clears any remaining post-crash corruption, so it is desirable.

**Conclusion:** the interactive Editor (launched normally by the user) is the only viable path. `CombatAutoSetup` makes that zero-effort.

## Block / dodge / stamina system (v7) — implemented, awaiting in-Editor verification

**User's brief (verbatim intent):** blocking cuts incoming damage to **10%** but drains stamina per hit; dodging **fully avoids** the hit and costs **no** stamina but needs correct timing; hitting **0 stamina while blocking stuns** you; dodging has a **cooldown** so it can't be spammed; **stamina regenerates whenever you are not blocking**; blocking = safe/easy, dodging = hard but rewarding. Plus: **"add a stamina bar at the buttom"**.

**New files** (all under `Assets/Scripts/Manuel/`):
- `PlayerCombat.cs` — the whole defensive system. **Q = hold to block, E = press to dodge** (chosen because Ctrl/Shift/Space/mouse were already taken by crouch/slide/jump/attack).
- `StaminaBarUI.cs` — bottom-screen bar, **built entirely in code at runtime** (uGUI only: no Canvas authored into the scene, no EventSystem, no TextMeshPro, no textures). Also draws an optional health bar and a status/hint line.
- `TrainingAttacker.cs` — stationary opponent that **telegraphs for 0.55 s** (body tints orange) then lands a hit. Exists purely so block/dodge have something to defend against. **T** forces a swing for testing.

**Key design decisions (worth keeping):**
- **`TakeDamage(float amount, Vector3 sourcePosition)` is the single damage entry point.** Dodge is checked *first* and returns 0 (full avoid); blocking then multiplies by `blockDamageMultiplier = 0.1`. Any future damage source MUST call this or the rules silently don't apply.
- **Dodge invulnerability is a shorter sub-window** (`0.22 s` of a `0.28 s` dodge). This is what makes "requires proper timing" real while still being a complete avoid.
- **Stamina regen is blocked *only* by `IsBlocking`** — deliberately *not* by the stun, so a stun is always recoverable.
- **The dodge never moves the player itself.** It sets `PlayerController.ExternalMotionLock = true` + `ExternalVelocity`, so gravity, camera feel and footsteps all keep working. `PlayerCombat` is `[DefaultExecutionOrder(-50)]` so it writes those *before* `PlayerController` reads them — otherwise the burst runs one frame long.
- `PlayerCombat.OnDisable()` clears the motion lock. Without it, disabling mid-dodge would freeze the player's horizontal movement permanently.

**`PlayerController.cs` gained exactly 4 public members** (it had none for external control before): `MoveInput` (read-only), `SpeedMultiplier` (auto-prop, default 1), `ExternalMotionLock`, `ExternalVelocity`. Plus `UpdateMovement` now has an `ExternalMotionLock` branch that cancels any slide, and the speed line became `(IsCrouching ? crouchSpeed : moveSpeed) * Mathf.Max(0f, SpeedMultiplier)`. Jumping is suppressed while externally locked.

**`CombatPrototypeSetup.cs` gained steps 5 and 6:** `BuildPlayerCombat()` (adds both components to `Player`, sets the `Player` tag) and `BuildTrainingAttacker()` (spawns the attacker **4 m in front of wherever the player actually starts**, facing them — computed at setup time, not hardcoded).

**Scene facts confirmed by reading `Manuel.unity`:** `Player` is at `(0, 1.02, 0)`, identity rotation (+Z forward), **already tagged `Player`**, and carries `PlayerController` (guid `7a1b3c5d9e0f4a2b8c6d1e3f5a7b9c0d`) plus a `PlayerInput`. So the attacker lands at `(0, 2.02, 4)` — inside its 6 m range immediately. `DamageDummy` at `(0,1,8)`, `WeaponHolder` under the camera. Scene was 33786 bytes.

**`CombatAutoSetup` now also refuses to fire during Play mode** (`EditorApplication.isPlayingOrWillChangePlaymode`) — it opens and saves a scene, which Unity refuses to do while playing. The completion marker was **deleted**, re-arming the one-shot auto-setup so it runs on the next domain reload.

**Note:** `PlayerCombat.cs`, `StaminaBarUI.cs` and `TrainingAttacker.cs` had **no `.meta` files** when written — Unity generates them on import. `PlayerController`/`WeaponController`/`DamageDummy`/`Billboard` all have hand-authored metas with stable GUIDs, and the scene references those GUIDs, so **never regenerate those metas**.

**`Tools/verify_scripts.py` (new)** — a "poor man's compile" to run before every hand-off, since Unity can't be driven from the shell. Checks: bracket balance per file (string/comment aware), every `_player.X` in `PlayerCombat` against `PlayerController`'s public members, every `_combat.X` in `StaminaBarUI` against `PlayerCombat`, and that every `AddComponent<T>()` target is either a declared class or a known engine type. 34 assertions, all green.
